# 청년정책 다중 분류 검색·관심 분야·추천

온통청년은 여러 분류를 쉼표로 이어 보낸다 (`lclsfNm`="일자리,교육", `mclsfNm`="취업,미래역량강화").
data-service는 이를 대·중분류 짝으로 나눠 버전별 `opportunity_categories`에 저장한다 (PR #132, `CategoryNormalizer`).
`opportunities.category`·`sub_category`는 원문 문자열 그대로다.

backend는 청년정책 분류를 **현재 버전의 분류 행으로만** 판단한다. 공고 컬럼 문자열로 대체(폴백)하지 않는다.
직업훈련은 분류가 하나라 행이 없고 기존처럼 공고의 대·중·세분류 컬럼을 쓴다.

## 배포 전제조건: 기존 버전 백필 완료

분류 행이 없는 청년정책은 공고 컬럼에 분류가 있어도 다음에서 빠진다.

- 통합 검색의 대·중분류 필터 (분류 필터가 없는 검색에는 그대로 나온다)
- 관심 분야 선택지
- 관심 분야가 있는 사용자의 개인화 추천 (관심 분야 미설정 사용자는 분류와 무관하게 추천된다)

따라서 이 backend를 배포하기 전에 다음 순서를 지킨다.

1. PR #132가 들어간 data-service를 먼저 배포한다. `YON_NORMALIZATION_CATEGORY_BACKFILL_ENABLED=true`(기본값)면
   기동 직후 비동기로 분류 행이 없는 청년정책 버전을 채운다. 새로 정규화되는 버전은 정규화가 직접 채운다.
2. data-service 로그에서 `Youth policy categories backfilled: versions=…, failedChunks=0`을 확인한다.
   실패한 묶음이 있으면 data-service를 다시 기동해 백필을 다시 돌린다 (행 없는 버전만 채우므로 반복해도 안전하다).
3. `database/scripts/youth-policy-categories-check.sql`을 application_user로 실행해 **`pending_backfill = 0`** 을 확인한다.
   `no_category`는 원본에 분류가 없는 정책이라 0이 아니어도 된다.
4. backend를 배포한다.

backend의 기존 정규화 코드(수집·정규화 이전 중)는 분류 행을 만들지 않는다. data-service를 띄우는 환경에서는
README 실행 플래그대로 backend의 정규화·백필 플래그를 `false`로 둔다.

## 매칭 규칙

| 기능 | 청년정책 | 직업훈련 |
| --- | --- | --- |
| 검색 대분류만 / 중분류만 | 현재 버전 분류 행 중 하나의 대분류 / 중분류가 같으면 포함 | `category` / `sub_category` 컬럼 |
| 검색 대·중분류 함께 | **같은 분류 행**에서 둘 다 같아야 포함. (일자리, 취업)·(교육, 미래역량강화) 공고는 교육 + 취업에 맞지 않는다 | 두 컬럼 |
| 검색 세분류 | 세분류가 없어 맞지 않음 (기존과 같음) | `detail_category` 컬럼 |
| 관심 분야 선택지 | 분류 행의 (대분류, 중분류) 짝. 대분류가 없는 행(중분류만 있는 행)은 계층에 놓을 수 없어 뺀다 | 대·중·세분류 컬럼 |
| 추천 HIGH | 분류 행 중 하나의 중분류가 관심 중분류 | 세분류가 관심 세분류 |
| 추천 MEDIUM | 분류 행 중 하나의 대분류가 관심 대분류 | 중분류가 관심 중분류 |

- 분류 행이 여러 개여도 검색 결과에 공고는 한 번만 나오고 건수가 정확하다 (조인하지 않고 현재 버전 ID를 IN으로 비교).
- 추천은 기존처럼 관심 대·중분류를 짝으로 묶지 않는다 (관심 분야는 유형별 코드 목록으로 저장된다).
- 응답의 `category`·`subCategory`는 기존 계약대로 공고 컬럼(원문 문자열)이다.

## 응답의 분류 행 (`categories`)

검색 목록(`GET /api/opportunities`)·공고 상세(`GET /api/opportunities/{id}`)·개인화 추천(`GET /api/users/me/recommendations`)·
저장 목록(`GET /api/users/me/saved-opportunities`) 항목에 `categories`를 더했다. 청년정책은 현재 버전의 분류 행을 `sort_order` 순서로
`{largeCategory, mediumCategory}` 배열로 주고(한쪽이 null인 행은 그대로), 직업훈련과 분류 행이 없는 정책은 빈 배열이다.
기존 필드의 값·의미는 바꾸지 않았으므로 하위 호환이다. 화면 표시는 이 값만 쓴다 (`frontend/docs/search.md`).

- 목록은 현재 페이지(추천은 최종 선정 결과)의 청년정책만 모아 한 번에 읽는다. 검색·저장 목록은 현재 버전 ID, 추천은 공고 ID로
  현재 버전을 조인해 읽는다(추천 후보에는 버전 ID가 없다). 청년정책이 없거나 빈 페이지면 읽지 않는다. 상세는 청년정책일 때 버전 ID로 1회.
- 검색 조건·정렬·COUNT·추천 선정 SQL은 바꾸지 않았다. 요청당 SQL 수(실험이 아닌 테스트 고정 데이터, `OpportunityCategoryDisplayPostgresTest`):
  검색 4 → 5, 저장 목록 2 → 3, 추천 10 → 11, 청년정책 상세 7 → 8, 직업훈련 상세 7(변화 없음). 항목 1건과 4건의 SQL 수가 같다.
  (추천은 직업훈련이 선정되면 기존 선정 경로가 훈련 일정을 1회 더 읽으며 분류와 무관하다.)

## 청년정책·직업훈련의 같은 대분류명 `교육･직업훈련`

청년정책 원본 대분류에는 옛 분류명 `교육･직업훈련`이 남아 있고(실험 DB 현재 버전 353건: 미래역량강화 256·교육비지원 69·온·오프라인교육 47),
직업훈련 대분류도 원본이 `교육･직업훈련`이다(137,043건). 같은 원본 이름이며, 프런트의 ‘직업훈련’은 직업훈련 대분류의 표시 이름일 뿐이다.
분류명은 통합하지 않고, 어느 공고 유형의 분류인지를 API로 전달해 구분한다. 중분류·세분류 이름은 두 유형 사이에 겹치지 않는다(실험 DB 확인).

- 관심 분야 선택지 `GET /api/interests/options`: 대분류·중분류 노드에 `opportunityTypes`(YOUTH_POLICY, VOCATIONAL_TRAINING 순)를 더했다.
  기존 필드와 구조(같은 이름 대분류는 한 노드)는 그대로라 하위 호환이다. 예: `교육･직업훈련` 노드는 두 유형, 그 아래 `온·오프라인교육`은 YOUTH_POLICY, `정보통신`은 VOCATIONAL_TRAINING.
- 통합 검색 `GET /api/opportunities`: 선택 파라미터 `categoryType`을 더했다. `type` 없이 검색할 때 분류(category·subCategory·detailCategory)를
  그 유형에서만 찾으므로 분류 필터에 맞는 공고는 그 유형뿐이다.
  - 생략하면 기존처럼 두 유형에서 찾는다 (기존 요청 호환).
  - `type`과 같으면 허용하고, 다르거나 분류 값 없이 쓰면 400, 잘못된 enum도 400이다.
  - 직업훈련 컬럼 비교에도 공고 유형 조건을 둔다. 청년정책 공고 컬럼에도 원문 `교육･직업훈련`이 있어서, 없으면 `categoryType=VOCATIONAL_TRAINING`에 청년정책이 섞인다.
- 추천: 바꾸지 않았다. 대분류 관심은 원래 청년정책에만 쓰이므로(직업훈련은 중·세분류만 매칭) 저장된 `CATEGORY 교육･직업훈련`은 청년정책 대분류로만 맞는다.
- 프런트: 대분류 이름으로 유형을 추측하던 로직(`categoryMatchesType`)을 없애고 `opportunityTypes`로 (유형, 대분류) 선택지를 만든다.
  검색 필터·관심 분야 화면·적용 조건·목록/상세 표시는 `frontend/docs/search.md`, `frontend/docs/profile.md`를 따른다. 관심 분야 저장값 형식은 바뀌지 않는다.

## 범위 밖

- 과거·현재 분류명 통합: 같은 데이터에 `금융･복지･문화`/`복지문화`, `참여･기반`/`참여권리`, `교육･직업훈련`/`교육`이 함께 있다.
  쉼표 분리 이전부터 단일 분류 데이터에도 있던 문제라 별도 정규화 규칙(data-service)으로 다룬다. 이번 작업은 이름을 바꾸지 않고 유형만 구분한다.

## 성능 (실험 DB, 2026-10-27 덤프 + 분류 행 5,417개)

측정 자료는 `perf-data/category-matching/`(저장소에 커밋하지 않음)에 있다.

- 검색 (JIT OFF, EXPLAIN ANALYZE)
  - 정책 대·중분류 + 최신순 첫 페이지: 0.2 → 4.3 ms. 기존은 유형·최신순 인덱스를 읽다 20건에서 멈췄고,
    지금은 분류 행에 맞는 버전(1,355개)을 모은 뒤 정렬한다. 대상이 청년정책 분류 행(전체 약 5천 개)으로 한정돼 상한이 작다. COUNT는 3.9 → 3.5 ms.
  - 유형 없는 대분류: 44 → 40 ms. 같은 조건을 상관 EXISTS로 쓰면 61 ms라 IN을 쓴다.
  - 직업훈련 분류: 52.7 → 55.4 ms (같은 수준).
  - 이름 충돌 해결 후 (`explain-category-type.txt`): `type=VOCATIONAL_TRAINING` 검색에는 같은 유형 조건이 두 번 붙지만 플래너가 합쳐
    계획(Filter)이 기존과 같다 (COUNT 65 / 76 ms는 같은 계획의 측정 편차). `categoryType=VOCATIONAL_TRAINING`은 같은 계획 56 ms,
    `categoryType=YOUTH_POLICY` + `교육･직업훈련`은 분류 인덱스로 353건을 1.6 ms에 센다. `categoryType` 없는 기존 요청은 이전 수정과 같은 SQL이다 (60 ms).
- 추천 상위 후보 SQL. 측정 DB에 사용자 테이블이 없어 최신 판정을 "현재 버전의 조건 묶음 전부 ELIGIBLE"로 바꾼
  최악 시나리오다 (실제 사용자보다 후보가 많다). 전/후를 번갈아 6회씩 실행했다.
  - 방식 비교 (인기 관심 분야, 중앙값): 기존 2.6초, CASE 안 EXISTS 5.0초, 분류 행 집계 조인(채택) 2.9초.
    SubPlan이 든 조건은 PostgreSQL이 하위 질의로 내려보내지 않는다. 그래서 EXISTS 방식은 match_level 필터가
    모든 공고 행(140,657)을 조인한 뒤에 적용됐다 (기존은 공고 스캔에서 29,549행으로 줄였다).
    집계 조인과 EXISTS 방식의 결과는 같다.
  - 채택안 최종 측정 (중앙값, 전 → 후): 인기 관심 분야 3,338 → 3,336 ms, 드문 관심 분야 2,902 → 3,366 ms,
    관심 미설정 3,183 → 3,483 ms. 같은 시나리오 안의 반복 편차(2.1~6.6초)가 전/후 차이보다 크고 범위가 겹친다.
    관심 미설정은 집계 하위 질의가 빈 결과(조건이 모두 false)라 실제 추가 작업이 거의 없다.
  - 결과 차이 (인기 관심 분야): "일자리,일자리 / 재직자,권익보호" 정책이 대분류 일자리로 MEDIUM이 되어 추가됐다.
    ELIGIBLE-MEDIUM 그룹(정책·훈련 공용)의 상위 5건 자리 하나를 이 정책이 차지해 훈련 한 건이 밀려났다. 드문 관심 분야·관심 미설정은 결과가 같다.
