수동 요청은 실행 이력을 생성한 뒤 전용 실행기로 수집을 수행한다. 페이지별 원본을 직전 스냅샷과 비교하여 신규·변경 시 원본과 PENDING 정제 요청을 함께 저장한다. 동일 원본은 관측 시각을 갱신한다. 출처·외부 ID를 유지하고, 출처 잠금으로 중복 실행을 방지하며 항목·페이지 오류와 처리 건수를 기록한다. 정제 요청 등록은 정제 완료나 사용자 알림 발생을 뜻하지 않는다.

## 정기 수집 스케줄러 구현

명세 근거: `Y_ON_Docs/기획서.md` 6.7의 일일 Full Sync 및 서버 시작 시 당일 동기화 확인, 요구사항 명세서 NFR-07의 하루 1회 수집 제안. 실행 시각은 이번 요청으로 확정했다.

- Spring Scheduler `@Scheduled(cron = "0 30 9 * * *", zone = "Asia/Seoul")` 사용.
- cron 순서: 초·분·시·일·월·요일. 매일 한국 시간 오전 9시 30분 실행.
- 온통청년·고용24를 각각 접수하며 기존 실행기·페이지 처리·원본 비교·실패 기록 경로를 재사용한다. 페이지 크기 100, 최대 페이지 수 1000이며 고용24의 상한은 기존처럼 NCS별로 적용된다.
- 자동 실행은 `sync_type=SCHEDULED`, 수동 실행은 `MANUAL`로 기록한다. 기존 수동 API 계약은 유지한다.
- 중단 이력 정리를 먼저 수행하고, 09:30 이후 서버 시작 시 한국 날짜의 당일 SUCCESS 이력이 없는 출처를 한 번 접수한다. 당일 수동 성공 이력도 보완 실행을 생략하는 근거로 사용한다. 09:30 이전 시작이면 정규 스케줄을 기다린다.
- 비활성 출처·이미 실행 중인 출처는 건너뛰고 다른 출처를 계속 접수한다. 접수 오류 로그에 외부 예외 메시지나 비밀값을 출력하지 않는다.
- `collection.schedule.enabled=false`로 스케줄과 시작 시 보완을 함께 끌 수 있다. 기본값은 활성화다. 기존 관리자 API 통합 테스트에는 이를 적용해 테스트 시작 시 자동 수집을 방지했다.

### 운영 범위와 남은 제약

기존 재시작 복구와 동일하게 단일 앱 인스턴스를 전제로 한다. 다중 서버에서는 실행 소유권·임대 기반 복구가 필요하다. 시작 시 보완은 당일만 대상으로 하며 과거 날짜별 누락을 재생하지 않는다. 실패 후 주기적 재시도는 추가하지 않았고, 다음 정규 실행·재시작 시 보완 또는 관리자 수동 실행을 사용한다. 페이지 API의 변동과 페이지 상한으로 생기는 누락 가능성은 기존과 같으며, 한 번 보이지 않은 데이터를 삭제·마감으로 확정하지 않는다.

기존 작업의 단일 PR을 만들 때 범위는 `fa83502`까지로 잡아야 한다. 현재 브랜치 HEAD에는 스케줄러 커밋도 이어져 있으므로 전체 HEAD를 그대로 선택하면 두 작업이 함께 포함된다. PR 생성과 푸시는 수행하지 않았다.

작업 전에 존재한 `Employment24ClientTests.java`, `docs/collection-flow.md`, `docs/images/`의 미커밋 변경은 보존했으며 이번 커밋에 포함하지 않았다. 테스트는 해당 기존 변경이 존재하는 작업 트리에서 실행했다.
