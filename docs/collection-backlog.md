# 수집 영역 남은 작업

기록일: 2026-10-18. 아래 항목은 후속 작업이며 이번 PR에서는 구현하지 않는다.

## 1. PostgreSQL LISTEN/NOTIFY

- 원본·정제 요청이 함께 커밋된 후 정제 소비자에게 처리 시작 신호를 전달한다.
- 영속적인 처리 대상은 `raw_normalization_request`이며 NOTIFY는 깨우기 신호로 사용한다. 연결 끊김·재시작으로 알림을 놓쳐도 PENDING 조회로 복구하도록 한다.
- 정제 담당과 채널·payload·소비 책임을 합의하고, 알림에 원본이나 비밀값을 넣지 않는다.
- 정제 워커의 작업 선점·중복 처리 방지·상태 전이·실패 재처리 계약을 확정한다. 수집 성공과 정제 성공은 구분한다. 정제 워커 자체의 구현 담당은 별도 협의한다.

## 2. 실패 청크 재실행

- 청크를 외부 API 한 페이지로 정의한다. 기존 DB 커밋 단위는 항목별이며 청크 전체 트랜잭션과 구분한다.
- 출처·페이지·페이지 크기·고용24 NCS·조회 기간·원래 실행 ID·상태·시도 횟수 등 재실행 조건과 이력을 보존한다.
- 조회 실패와 조회 후 저장 실패를 구분한다. 저장 실패 원본의 보존 범위·보관 기간을 결정하고, 재조회와 보존 payload 재처리를 구분한다.
- 실패 청크만 다시 접수하는 관리자 API와 원본 실행 연관 이력을 추가한다. 중복 접수·동시 실행을 방지하고 기존 원본 비교·정제 요청 멱등성을 유지한다.
- 외부 페이지 구성이 바뀌면 같은 페이지를 다시 조회해도 같은 항목이 돌아온다는 보장이 없음을 명시한다. 실행 도중 중단되었을 때 실패 목록이 최종 집계 전에 소실되지 않도록 청크 상태를 영속화한다.

## 3. 테스트 코드 정리

- 단위·Spring 보안/컨텍스트·실제 PostgreSQL 통합 테스트·벤치마크의 실행 조건과 설정을 정리한다.
- Docker/Testcontainers 및 PostgreSQL 테스트 DB 실행 방법을 통일하고, 테스트에서 운영 데이터와 외부 API를 사용하지 않도록 한다.
- LISTEN/NOTIFY 유실·재연결, 청크 재실행·동시 접수, 원본+정제 요청 롤백, 관리자 권한과 공통 오류 응답을 검증한다.
- 현재 알려진 환경 제약: Docker 부재로 인증 동시성 테스트 초기화 실패, 전용 DB/실행 조건 미설정으로 일부 통합 테스트·벤치마크 건너뜀.

## 추가 운영 확인

- 기존 SQL 스크립트와 실제 운영 스키마의 적용 순서·제약·인덱스를 확인한다. 검증 없이 DB 마이그레이션을 수행하지 않는다.
- 정제 요청 적체·장기 PENDING, 마지막 수집 성공 시각, 청크 실패·재시도 결과를 운영자가 확인할 기준을 정한다.
- 다중 앱 인스턴스를 운영할 때에만 실행 소유권·임대 기반 중단 복구를 추가한다. 현재 단일 인스턴스 재시작 복구를 다중 서버 안전성으로 간주하지 않는다.
