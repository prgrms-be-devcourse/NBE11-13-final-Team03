# 저장·숨김과 저장한 기회

## 계약과 적용 화면

로컬 PreferenceController·PreferenceService·SavedOpportunityResponseDto·SavedOpportunitiesResponseDto, 관련 Controller·행동 이벤트 테스트, RecommendationController와 공개 검색·상세 Controller를 확인했다. 백엔드는 수정하지 않았다.

- POST/DELETE `/api/opportunities/{id}/save`, POST/DELETE `/api/opportunities/{id}/hide`는 인증·CSRF가 필요하며 성공은 정확한 204다. 본문을 읽지 않는다. 400·401·403·404(USER_001/PREFERENCE_001)·통신 실패는 성공으로 처리하지 않는다.
- POST의 source는 검색 SEARCH, 추천 RECOMMENDATION, 공개 홈·상세 OTHER다. 저장 목록은 SAVED 출처로 저장 해제를 사용하되 DELETE 계약에는 source가 없어 전송하지 않는다.
- SAVE/HIDE 행동 이벤트는 실제 상태가 바뀔 때 서버가 기록한다. 별도의 행동 이벤트 요청은 추가하지 않는다. 저장·해제는 숨김을 바꾸지 않고 숨김·해제도 저장을 바꾸지 않는다.
- 검색·상세·홈 공개 카드·추천에서 저장과 해제를 제공한다. 숨김은 추천 카드에서만 제공한다. 검색·상세는 숨긴 공고도 계속 조회한다.
- 숨김 목록/현재 숨김 상태 조회 Controller는 없다. 내부 Service의 일괄 조회는 HTTP API가 아니므로 UI에서 사용하지 않는다. `unhideOpportunity` 함수는 제공하지만 대상을 추측하는 숨김 해제 UI는 만들지 않는다.

## 저장 목록

`/saved`는 인증 상태 확인·실패·비로그인 안내를 구분한다. 확인된 사용자에게만 GET `/api/users/me/saved-opportunities?page=0&size=20`을 실행한다. 서버의 저장 시각 내림차순·저장 상태 ID 내림차순 순서를 유지한다.

목록에는 opportunityId/type/title/category/subCategory/savedAt만 표시하며 없는 마감일·판정·숨김 여부는 만들지 않는다. 저장 시각은 서버 LocalDateTime 문자열을 표시하며 임의로 시간대를 변환하지 않는다. 상세 링크와 저장 해제, 0-based API 페이지를 1-based로 표시하는 이동 버튼을 제공한다. 조회 중 버튼을 비활성화하고 로딩·빈 목록·오류·재시도를 구분한다.

빈 페이지가 되면 서버 totalPages를 바탕으로 이전 유효 페이지로 보정한다. 동시 삭제로 여러 페이지가 사라지거나 전체 목록이 비어도 0 이하로 이동하지 않는다. 다른 페이지의 이전 데이터를 새 페이지의 결과로 표시하지 않는다.

## 변경 요청과 캐시

기존 apiClient의 쿠키·CSRF 확보·요청 시 최신 토큰·제한적 401 재발급·timeout을 사용한다. 토큰이나 인증 플래그를 별도로 저장하지 않는다.

동일 QueryClient·사용자·공고에서 같은 변경은 하나의 Promise를 공유하고, 처리 중 반대 변경은 거절한다. useIsMutating으로 같은 공고의 여러 버튼도 함께 비활성화하고 버튼별 동기 가드로 연속 클릭을 막는다. 잠금은 성공·실패 모두 해제하며 새로운 사용자 객체의 작업과 이전 Promise의 정리를 구분한다. 서로 다른 공고의 변경까지 전역으로 막지 않는다.

낙관적 업데이트는 사용하지 않는다. 변경 전 진행 중인 관련 GET을 취소하고, 204 확인 뒤 다시 취소·invalidate하여 늦은 이전 조회가 saved를 덮어쓰지 않게 한다. 저장 변경은 현재 사용자의 저장 목록·추천, 검색·공개 홈 목록, 해당 공고 상세를 대상으로 한다. 숨김 변경은 현재 사용자 추천만 갱신한다. 프로필·지역·분류 옵션이나 다른 공고 상세까지 전체 초기화하지 않는다. 활성 조회의 갱신 완료까지 변경 작업을 pending으로 유지한다. 갱신 실패도 안내하며 서버의 변경 자체를 되돌렸다고 주장하지 않는다.

전송된 변경은 카드 제거·화면 이동만으로 취소하지 않는다. 서버 완료를 확인한 뒤 새 화면의 캐시도 갱신하기 위해서다. 응답 전후에 확인된 사용자 객체·인증 확인/전환 상태를 검사해 계정이 바뀌면 이전 결과의 캐시 갱신을 중단한다. 외부에서 전달한 AbortSignal 취소도 검사한다. UI의 생존 여부로 서버 성공 여부를 판단하지 않는다.

저장 목록 키는 `['saved-opportunities', userId, page, size]`이며 gcTime=0이다. 기존 인증 전환 정리에 저장 목록의 취소·제거를 추가했다. 공개 검색·상세·홈의 기존 개인화 캐시 초기화 정책은 유지한다. 로그인·로그아웃·새 사용자 확인 뒤 이전 저장 목록을 재사용하지 않는다.

## 검증과 한계

Node 테스트는 네 API의 경로·메서드·204·source·CSRF·인증 옵션, 저장/숨김 독립성, 오류·잘못된 응답, 페이지와 마지막 항목 제거, 중복 요청 공유·반대 변경 차단·실패 복구, 대상 Query만 갱신, 늦은 GET/이전 사용자 응답 차단을 확인한다. TSX 서버 렌더링으로 비로그인/확인 중/오류 접근 제한, 로그인 복귀, DTO 필드 표시와 접근 가능한 동작 이름을 확인한다.

격리된 Chrome·Vite 테스트에서 실제 AppRoutes·AuthProvider·Query·apiClient·카드를 사용하고 HTTP adapter만 모의 처리한다. 저장 목록 페이지 이동·마지막 항목 해제·보정, 상세 저장/해제, 추천 숨김과 독립 상태, 요청 중 화면 이동 후 검색 갱신, source, 로그아웃 캐시 제거와 비로그인 복귀 링크, 행동 이벤트 중복 전송 방지를 검증한다. 이는 실제 인증된 서버 저장 검증이 아니다.

`npm run lint`, `npm run build`(strict 타입 검사 포함)가 통과했다. `npm test`는 기존 148개와 신규 16개를 포함한 164개가 통과했고 생략한 테스트는 없다.

실제 서버 읽기 확인에서 저장 목록은 인증 쿠키 없이 401, 공개 검색은 200이었다. 허용된 로그인 테스트 계정이 없어 실제 저장·숨김·해제 요청은 실행하지 않았다. 수동 모바일·키보드 조작, 실제 인증·쿠키·CSRF·토큰 회전과 서버 변경 통합은 후속 검증 대상이다. 서버가 이미 처리한 요청의 응답이 유실되면 결과를 확정할 수 없으므로 최신 상태를 재조회해야 한다. 다른 탭·기기의 변경을 즉시 공유하거나 서버 완료를 취소로 되돌리지는 않는다.
